## Найденные дефекты

Все — в автоматических тестах не ловились: 227 тестов работали через
`NullBackend`, слой `audio/mpv.py` и конкурентный доступ к SQLite
не покрывались вообще.

### 1. Читатель IPC умирал через 3 с тишины

`MpvBackend` ставил `settimeout(3)` на сокет для таймаута команд, и этот же
таймаут наследовал `recv()` в потоке чтения. Пауза между треками длиннее
3 с считалась обрывом: поток чтения выходил, `end-file` больше не приходил.
Симптом: сессия играет один трек и навсегда остаётся в состоянии `playing`,
а любая следующая команда падает с `mpv не ответил`.

Исправление: чтение блокирующее, таймаут остался только у команд
(`Event.wait` в `_command`).

### 2. Дедлок в обработчике завершения трека

`on_end` вызывался прямо из потока чтения IPC. Обработчик переключал трек,
то есть отправлял `loadfile` и ждал ответ — а прочитать ответ мог только
тот же поток, занятый ожиданием. Через 3 с — `PlayerError`, следующий трек
не запускался.

Исправление: события `end-file` обрабатывает отдельный поток-диспетчер.

### 3. `sqlite3.ProgrammingError` при автопереходе

Вместе с дефектом 2 переключение трека ушло в другой поток, и
`store.record_play()` падал с `check_same_thread`. Исключение не относилось
к `NeuroWaveError`, поэтому молча глоталось диспетчером: история не
писалась, событие следующего трека терялось.

Исправление: соединение открывается с `check_same_thread=False`, все
операции сериализованы `RLock`.

### 4. Переданная очередь молча заменялась

`self.queue = queue or Queue(...)` — `Queue` реализует `__len__`, поэтому
пустая очередь ложна, и переданный объект с `repeat`/`shuffle` игнорировался.

Исправление: явная проверка `is not None`.

### 5. Качество в событии чужого трека

`_emit("track", quality=self._current_quality)` читал общее поле в момент
отправки: если диспетчер успевал перейти на следующий трек, событие
подписывалось его качеством (наблюдалось как `truncated … [MP3 191 kbps]`).

Исправление: в событие уходит снимок значения, старт трека сериализован
блокировкой.

### 6. mpv-сироты после SIGTERM/SIGHUP

Закрытие терминала оставляло `mpv --idle=yes` жить вечно (за прогон
накопилось 11 процессов). SIGINT обрабатывался, SIGTERM и SIGHUP — нет.

Исправление: сигналы превращаются в `KeyboardInterrupt`, чтобы отработали
`finally` и `MpvBackend.shutdown()`.

### 7. `login` падал сразу после успешного входа

`account_status().plus` — объект `Plus(has_plus=…)`, а не `bool`; код клал
его в `AccountInfo.plus`, а CLI делал по нему словарный поиск → `KeyError`
и трейсбек уже после сохранения токена.

Исправление: нормализация в `bool|None` (`_plus_flag`), а вывод статуса
больше не падает ни на каком типе.

### 8. `me` не показывал аккаунт

`client.me` в `yandex-music` — это `Status`, а пользователь (`uid`, `login`,
`display_name`) лежит в `me.account`. Код читал поля у `Status`, получал
`None` и печатал «Аккаунт Яндекс Музыки» без логина.

Исправление: берём `me.account`, при его отсутствии — `me`.

## Что осталось непроверенным

* SoundCloud и Spotify — нужны ключи приложения и Premium-устройство.
* Lossless: качество показывается по фактическому кодеку потока, отдельной
  проверки на FLAC-подписке не было.
* Bluetooth/HDMI-переключение: интерфейса выбора устройства ещё нет.
* Изоляция секретов: `TokenStore` пишет в общий keyring и игнорирует
  `--home`, поэтому профили и тесты делят один токен. На машине с рабочим
  Secret Service из-за этого падают 2 теста (`test_soundcloud`,
  `test_spotify`); с `PYTHON_KEYRING_BACKEND=keyring.backends.fail.Keyring`
  набор зелёный. Требует отдельного решения.

## Как воспроизвести

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -e '.[dev,mpris,desktop]'
neurowave doctor

# локальные файлы, без сети и аккаунта
neurowave --provider local play "запрос" --seconds 30

# живой аккаунт
neurowave login          # OAuth Device Flow: ссылка и код в терминале
neurowave me
neurowave wave --seconds 60

# тесты, в том числе без доступа к системному keyring
PYTHON_KEYRING_BACKEND=keyring.backends.fail.Keyring python -m pytest
```
