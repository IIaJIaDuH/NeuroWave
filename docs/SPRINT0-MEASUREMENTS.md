# Sprint 0: замеры на целевой машине — 16.11.2026

Замеры для гейта Sprint 0 ([ROADMAP](ROADMAP.md)): память, CPU, старт и
воспроизведение на Bluetooth/HDMI, доступ к PCM для DSP, аудит лицензий.
Все цифры получены на реальном аккаунте и реальных устройствах, не в
эмуляции.

## Стенд

| | |
|---|---|
| ОС | Linux Mint 22.3 (Zena), ядро x86_64 |
| CPU | AMD Ryzen 7 5800X (8 ядер / 16 потоков) |
| RAM | 31 ГБ (занято посторонними приложениями ~13 ГБ во время замеров) |
| Звуковой сервер | PipeWire 1.0.5 + WirePlumber, профиль `a2dp-sink` |
| Устройства | Bluetooth **Bose QuietComfort Ultra** (`bluez_output.59_19_70_A9_CF_F8.1`, кодек **SBC**), HDMI **HDA NVidia** (`alsa_output.pci-0000_09_00.1.hdmi-stereo`) |
| Плеер | NeuroWave 0.1.0, mpv 0.42.0 (статическая сборка), Python 3.12.3 |
| Для сравнения | Chromium 157.0.8103.50 |

## Методика

**PSS и CPU** — `packaging/smoke-measure.sh`: сумма PSS по дереву процессов
из `smaps_rollup`, CPU по тикам `/proc/<pid>/stat` за интервал, раз в 5 с
опрос mpv по JSON IPC (кодек, битрейт, частота, `underrun` демуксера).

**Условия прогонов**: пустой кеш перед каждым устройством, реальный поток
(`MP3 320 kbps`), громкость 35 %, длительность 100–105 с на устройство,
дефолтный выход переключался через `pactl set-default-sink` и возвращался
обратно.

**Старт** — отдельный harness: `MpvBackend` с явным
`--audio-device=pulse/<sink>`; время считается до `time-pos > 0`, а
фактическое устройство проверяется свойством `audio-device` самого mpv
(иначе легко измерить дефолтный выход вместо нужного).

**Браузер** — Chromium с локальной страницей `<audio autoplay loop>`,
дерево процессов — по корневому процессу с `--user-data-dir`.

## Результаты

### Память и CPU (100 с непрерывного воспроизведения)

| Сессия | PSS средний | PSS пик | из них mpv | из них python | CPU средний | CPU пик | underrun |
|---|---|---|---|---|---|---|---|
| NeuroWave · Bluetooth | **127.7 МБ** | 129.9 МБ | 83.6 МБ | 44.0 МБ | **1.87 %** | 2.2 % | 0 из 20 |
| NeuroWave · HDMI | **121.8 МБ** | 127.9 МБ | 78.9 МБ | 43.0 МБ | **1.81 %** | 2.4 % | 0 из 19 |
| NeuroWave · локальные файлы | 89.8 МБ | 90.7 МБ | 60.8 МБ | 28.2 МБ | 2.0 % | 2.0 % | — |
| Chromium · то же аудио | **458.0 МБ** | 459.1 МБ | — | — | **3.40 %** | 10.6 % | — |

Разница «сеть / локальные файлы» ≈ **37 МБ**: сетевые буферы mpv плюс
предзагрузка следующего трека в кеш. Браузер на том же материале — в **3.6
раза** больше по памяти и с пиками CPU в 5 раз выше.

Устройство вывода на память почти не влияет: BT против HDMI — 6 МБ разницы,
в пределах сетевого разброса. CPU в обоих случаях ~2 % одного ядра.

Ориентир ТЗ «до 200 МБ» выполняется с запасом в обоих случаях.

### Старт

| Что | Время |
|---|---|
| `neurowave --version` (запуск интерпретатора и импортов) | 0.07 с |
| `neurowave status` (локальное состояние) | 0.16 с |
| `neurowave me` (сеть до API) | 0.68 с |
| До первого звука, локальный файл · Bluetooth | 367 мс |
| До первого звука, локальный файл · HDMI | 205 мс |
| До первого звука, сетевой поток · Bluetooth | 705 мс |
| До первого звука, сетевой поток · HDMI | 572 мс |

`MpvBackend.load()` в обоих случаях 101 мс — это стоимость старта mpv и
round-trip по IPC. Разница BT/HDMI ≈ 160 мс — это кодек SBC и
согласование A2DP, а не наш код. Сетевой поток добавляет ~350–500 мс на
получение ссылки и буферизацию.

### Задержка вывода

Из `pw-top` во время воспроизведения:

| Узел | Квант | Частота | Период |
|---|---|---|---|
| клиент mpv | 2646 кадров | 44100 Гц | **60 мс** |
| узел вывода (BT и HDMI одинаково) | 128 кадров | 48000 Гц | **2.7 мс** |

То есть PipeWire отдаёт звук короткими блоками, а основной буфер — на
стороне mpv (60 мс). Задержку BT-кодека PipeWire не показывает: она
проявляется только в разнице старта (см. выше) и в тракте наушников.

### Формат потока

`mp3 320 kbps`, 44.1 кГц, 2 канала → PipeWire `float32` → BT-узел `S16LE
48 кГц`, HDMI-узел `S32LE 48 кГц`. Ресемплинг делает PipeWire, NeuroWave
поток не трогает.

## Доступ к PCM и встраивание DSP

| Способ | Проверено | Следствие |
|---|---|---|
| `mpv --af=lavfi=[equalizer=…],alimiter` | есть `lavfi`-мост и фильтры `equalizer`, `alimiter`, `loudnorm`, `dynaudnorm`, `adeclip` | DSP можно включить аргументами запуска, без изменения кода плеера |
| `mpv --ao=pcm --ao-pcm-file=…` | получен WAV: 1 канал, 44100 Гц, 16 бит, 6.0 с | декодированный PCM доступен для спектроанализатора |
| PipeWire `libpipewire-module-filter-chain.so` | модуль установлен | системный DSP-граф вне приложения, работает и для других клиентов |
| `libmpv.so.2` | есть в системе (`/lib/x86_64-linux-gnu/libmpv.so.2`) | вариант встраивания, но со сменой лицензионной модели (ниже) |

Вывод: для Sprint 2 не нужно писать свой декодер. Достаточно цепочки
`lavfi` в mpv (или `filter-chain` в PipeWire) плюс управление параметрами из
ядра. Точка съёма PCM для спектроанализатора — `ao=pcm` или
`--audio-add`/подписка на поток.

Главное для решения о лицензии: **`mutagen` — единственный GPL-компонент,
который попадает внутрь нашего процесса.** Он необязателен (extras
`[local]`), поэтому закрытая сборка без него возможна — теги тогда берутся
из имён файлов. Если встраивать `libmpv` вместо запуска процесса, GPL
распространяется и на приложение.

## Что осталось не измеренным

* **CloudMus и YaMusic** не установлены на машине (нет в `apt`, `flatpak`,
  `snap`), сравнение с ними не проводилось: нужно сначала выбрать конкретные
  проекты и способ установки.
* **Bluetooth-кодеки** кроме SBC не проверялись: профиль `a2dp-sink` с SBC —
  текущее состояние системы, AAC/LDAC не включались, влияние кодека на
  качество и задержку не измерялось.
* **HDMI с подключённым дисплеем**: выход был в состоянии `SUSPENDED`,
  воспроизведение шло, но физический вывод на телевизор/монитор не
  подтверждался.
* **Долгие сессии**: замеры по 100 с; утечки на часах не проверялись.

## Ограничения метода

* Машина не была выделенной: во время замеров играло другое приложение
  (`Everlusting Life.exe`), фоновая нагрузка не контролировалась. PSS/CPU
  считаются только по дереву процессов NeuroWave, но абсолютные проценты
  CPU на нагруженной системе могут быть завышены.
* PSS-сэмплы берутся раз в 5 с, пики между сэмплами не видны.
* Замер «локальные файлы» сделан на 20 с (2 сэмпла) — годится для оценки
  порядка величины, не для среднего.

## Как воспроизвести

```bash
# сессия + замеры PSS/CPU/кодека
neurowave wave --seconds 150 --no-interactive &
packaging/smoke-measure.sh --seconds 100 --interval 5 --csv ~/nw.csv

# другое устройство: переключить выход и повторить
pactl set-default-sink alsa_output.pci-0000_09_00.1.hdmi-stereo
```

`smoke-measure.sh` теперь принудительно пишет CSV с точкой как десятичным
разделителем (`LC_NUMERIC=C`): до этого при русской локали он выдавал
`125,9`, и файл нельзя было разобрать.

## Проверка графа DSP (PR-03)

Стенд: тон 1 кГц на −6 dBFS, 48 кГц/моно, mpv 0.42 с `--ao=pcm
--ao-pcm-file=…`, RMS и пик считаются по выгруженному PCM. Графы строит
`audio/dsp_graph.py` из типизированного профиля.

| Профиль | Граф | RMS | Пик |
|---|---|---|---|
| без обработки | — | −9.03 dBFS | −6.02 dBFS |
| +12 дБ на 1 кГц, preamp −12 дБ | `volume=-12dB, equalizer=g=12` | −9.03 dBFS | −6.02 dBFS |
| −12 дБ на 1 кГц | `equalizer=g=-12` | −21.03 dBFS | −11.90 dBFS |
| +12 дБ, лимитер −1 dBFS | `volume=+12dB, alimiter=limit=0.891:level=0` | −4.02 dBFS | **−1.00 dBFS** |

Что это доказывает: усиление и срез попадают в звук с точностью до 0.01 дБ
(знак и величина preamp верны), а `alimiter` с `level=0` держит пик ровно на
потолке, не поднимая выход автовыравниванием. Это ещё **не** доказательство
безопасности усиления выше 100 %: нужны inter-sample peaks, oversampling и
проверка на реальном материале (PR-04).
