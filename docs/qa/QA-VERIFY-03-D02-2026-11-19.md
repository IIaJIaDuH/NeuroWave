## 6. Целостность данных

Артефакт: `qa/artifacts/verify_d02_integrity.json`.

* SHA256 `config.json` зафиксирован до и после **каждой** команды каждого кейса;
  для пяти P1-случаев значения совпадают — повреждённый файл не изменён.
* Токены, БД (`state.db`) и история: `tokens_lost = false`, `user_data_intact = true`,
  утечек токена в stdout/stderr нет ни в одном из 72 запусков.
* Новые файлы профиля — только `data/state.db`, создаваемый штатно при запуске
  `app`; удалённых файлов нет ни в одном кейсе.
* Ручная правка повреждённого конфига → `status` возвращает код 0 без traceback,
  маркер пользовательских данных сохраняется, профиль не удаляется.

**Замечание P2 (отдельно от D-02, поведение одинаковое на `main` и на исправлении).**
Штатное сохранение приложением (`app` при выходе) переписывает `config.json` своей
схемой, и неизвестные пользовательские поля при этом теряются: в кейсе
`extra_fields` ключи `another` и `что_то_новое` отсутствуют в файле после запуска.
Это делает команда `app` (и только она — `config_rewritten_by = ["app"]`), одинаково
на `main` и на проверяемом SHA, к повреждённой конфигурации отношения не имеет и
в приёмку D-02 не входит. Требуется отдельная задача.
