### 2.3 Что именно ломается

* Тип поля не проверяется ни при чтении, ни при использовании: `Settings`
  (`config.py:71-115`) — обычный dataclass без валидации, `from_dict()`
  (`config.py:118-141`) фильтрует только *неизвестные имена*, но не *типы*.
* `int(value)` в `clamp_volume()` (`config.py:96`) бросает `ValueError`/`TypeError`
  на строке или `None`.
* Ошибка возникает **за пределами** блока `try/except` в `ConfigStore.load()`
  (`config.py:154-160`): `except (OSError, json.JSONDecodeError)` ловит только
  проблемы чтения и синтаксиса, поэтому `Settings.from_dict()` падает наружу.
* `cli.main()` (`cli.py:232-238`) перехватывает только `NeuroWaveError`
  (→ «Ошибка: …», код 2) и `KeyboardInterrupt`. `ValueError`/`TypeError` — не
  `NeuroWaveError`, поэтому пользователь получает Python-traceback и код 1.
* **`doctor` падает так же** (`cli.py:1275` → `ConfigStore(paths).load()`):
  диагностическая команда, которой пользуются именно для разбора проблем,
  на битой конфигурации не работает. Проверки, собранные до этого места,
  пользователю не показываются — вывода нет вовсе.
* Часть полей (`cache_quota_gb`, `cache_ttl_days`) проверяются только **в момент
  использования** (`config.py:107-113`), поэтому для них падает не `status`, а
  `app`/`status` в момент обращения к кэшу — ошибка «поздняя» и её harder
  связать с конкретным полем.

### 2.4 Что происходит с файлом и данными пользователя

| Проверка | Результат |
|---|---|
| Файл конфигурации изменён при падении | **нет** — sha256 совпадает до и после (проверено для всех 5 аварийных случаев) |
| Частично записанная конфигурация | **нет** — файл остаётся байт-в-байт прежним |
| Потеря «пользовательских данных» | **нет** — маркер в профиле цел во всех 24 случаях |
| Восстановление после починки | **да** — после замены конфигурации на корректную `status` отрабатывает с кодом 0, данные целы (24/24) |
| Восстановление удалением файла | **работает** — при отсутствии файла приложение создаёт конфигурацию по умолчанию и стартует |

Отдельно (наблюдение, не новый дефект): **команда `app` при выходе переписывает
`config.json`** (`cli.py:972`: `ConfigStore(ctx.paths).save(ctx.settings)`), и
сохранённые настройки — уже нормализованные. Из этого следуют тихие потери:

* неизвестные поля (`что_то_новое`) **удаляются** из файла;
* `repeat: 5` и `repeat: "карусель"` заменяются на `off`;
* `volume: 500` заменяется на `130` (потолок `MAX_VOLUME`), `volume: 80.7` — на `80`,
  `volume: true` — на `1`;
* битый профиль из `custom_profiles` удаляется.

`status` и `doctor` файл не переписывают (проверено отдельно) — переписывает
только `app` при выходе. Это важно для любого исправления: «починить D-02» не
должно означать «ещё больше молчаливых потерь в файле пользователя».

### 2.5 Степень влияния

**P1.** При пяти вариантах конфигурации приложение не запускается вовсе; при этом
пользователь получает не сообщение, а служебный traceback с внутренними путями и
полным именем файла. Хуже всего то, что `doctor` — инструмент разбора — падает
так же, то есть «сломать конфигурацию» = «нечем диагностировать». Данные при
этом не теряются: повреждается только возможность запуска.

### 2.6 Рекомендация по исправлению

1. **Проверять типы при чтении**, а не при использовании: в `Settings.from_dict()`
   приводить каждое поле к ожидаемому типу с безопасным откатом на значение по
   умолчанию (и, по возможности, с предупреждением в журнал/интерфейс), —
   `volume`, `cache_quota_gb`, `cache_ttl_days`, `shuffle`, `repeat`, `provider`.
2. **Ловить `ValueError`/`TypeError` в `ConfigStore.load()`** и превращать их
   в `ConfigError` — тот тип, который CLI уже умеет показывать по-человечески
   («Ошибка: …», код выхода 2). Ошибка чтения настроек не должна выглядеть как
   падение программы.
3. **Не трогать файл пользователя при ошибке**: показывать понятное сообщение
   с путём к файлу и способом починки; переписывать конфигурацию — только
   осознанно и без молчаливой потери неизвестных полей.
4. **`doctor` не должен падать** из-за битой конфигурации: отдельная проверка
   «настройки читаются / не читаются» с кодом проверки, а не traceback.

### 2.7 Возможные регрессии после исправления

* «Мягкий» откат (`"громко"` → 80) может **скрыть опечатку**: пользователь не
  заметит, что его громкость не применилась. Нужен явный признак в интерфейсе
  («значение настройки неверно, применено 80 %»), иначе дефект просто станет
  тихим.
* Если начать чинить `config.json` автоматически, можно **потерять неизвестные
  поля** — сейчас это уже происходит при выходе из `app`; исправление не должно
  расширять это поведение.
* Проверка типов может отвергнуть значения, которые сегодня «работают» по
  счастливой случайности (например, `volume: "80"` как строка — сейчас `int("80")`
  проходит). Стоит решить, принимаются ли числовые строки, и зафиксировать это
  тестом, иначе у пользователей «сломается» конфиг, который молча работал.
* `cache_quota_gb`/`cache_ttl_days` сейчас проверяются лениво; перенос проверки
  на этап чтения изменит момент, когда пользователь увидит ошибку (сразу, а не
  при первом обращении к кэшу) — это правильнее, но меняет наблюдаемое
  поведение.

### 2.8 Предлагаемые автоматические тесты приёмки

1. Параметризованный тест `Settings.from_dict` / `ConfigStore.load` на наборе
   невалидных значений (`volume`, `cache_quota_gb`, `cache_ttl_days`, `shuffle`,
   `repeat`, `provider`): ожидается `ConfigError` или приведение к значению по
   умолчанию; **не** `ValueError`/`TypeError`.
2. Тест CLI: `status`, `doctor`, `app` на битой конфигурации → код выхода 2,
   в stderr — сообщение без слова `Traceback`; путь к файлу в сообщении
   допустим, внутренние пути модулей — нет.
3. Тест целостности: после неудачного запуска содержимое `config.json` совпадает
   с исходным (sha256), в каталоге данных не появилось частичных файлов.
4. Тест восстановления: после починки конфигурации приложение стартует, данные
   пользователя на месте.
5. Тест «неизвестные поля не теряются»: после цикла запуска `app` ключи,
   которых нет в модели `Settings`, сохраняются в файле.
6. Тест `doctor`: битая конфигурация → проверка «Настройки» помечена как
   неуспешная, команда возвращает ненулевой код и печатает остальные проверки.

## 3. D-06 — неизвестная длительность композиции: **подтверждён**

### 3.1 Минимальное воспроизведение

Длительность `None` — законное значение домена: `Track.duration_ms: int | None`
(`domain.py:28`), то есть провайдер вправе не отдавать длительность.

```python
track = dataclasses.replace(real_track, duration_ms=None)
player.play_tracks([track], start=0)      # обычное окно: neurowave app
```

Через 200 мс (тик таймера обновления) в stderr процесса:

```
  File ".../src/neurowave/ui/app.py", line 157, in refresh
    time_label.setText(f"{_mmss(snap.position_ms)} / {_mmss(snap.duration_ms)}")
  File ".../src/neurowave/ui/app.py", line 38, in _mmss
    seconds = max(0, milliseconds // 1000)
TypeError: unsupported operand type(s) for //: 'NoneType' and 'int'
```

Цепочка данных: `PlayerViewModel.snapshot()` (`viewmodel.py:167`) кладёт в снимок
`duration_ms=track.duration_ms if track else 0` — то есть `None` проходит дальше
без нормализации, хотя `UiState.duration_ms` объявлен как `int` (`viewmodel.py:32`).

### 3.2 Что происходит в окне (реальное окно Qt, X11)

| Сценарий | Результат |
|---|---|
| `duration_ms=None` | `TypeError` в каждом обновлении; время в окне остаётся прежним («0:00 / 0:45» — длительность *предыдущего* трека), ползунок не двигается, кнопка паузы не меняет значок, статусная строка не обновляется |
| Частота исключений | **5 в секунду** — по одному на тик таймера обновления (200 мс); за прогон — 45 исключений. Отдельный замер: в фазе с неизвестной длительностью **47 вызовов обновления из 47 завершились ошибкой** (100 %) |
| Qt event loop | **не заблокирован**: «сердцебиение» 150 мс даёт 5.96–7.44 тика/с при ожидаемых 6.67 — и в норме, и в аварийном состоянии (по фазам: 6.73 / 6.74 / 6.63). Один вызов обновления занимает 10.8–14.4 мс. Зависания цикла из-за D-06 **нет** |
| `duration_ms=0` | Исключений нет. Время показывается как «0:00 / 0:00», ползунок стоит на нуле, перемотка недоступна (длина `state["length"] = 0`) |
| Трек на 6 часов | Исключений нет, отображается «360:00» |
| Пустая очередь | Исключений нет, окно живо («0:00 / 0:00») |
| Pause/Resume при неизвестной длительности | Проигрывание встаёт на паузу и снимается с паузы (команды исполняются), но **значок кнопки не меняется** — интерфейс показывает то, что было до ошибки |
| Возврат к треку с известной длительностью | Исключения прекращаются (0 за фазу), обновления восстанавливаются — ползунок снова движется |
| Пользователю что-нибудь показывают? | **Нет.** Ни в статусной строке, ни во всплывающем сообщении |

Скриншот состояния ошибки: `docs/qa/screenshots/triage02_d06_error_state.png`
(только окно приложения; в нём видно устаревшее «0:00 / 0:45» и кнопку
в состоянии «воспроизведение», хотя трек на паузе).

### 3.3 Степень влияния

**P1** для случая, когда провайдер не отдаёт длительность: звук играет, но
интерфейс «примерзает» на устаревшем состоянии — время, ползунок перемотки,
значок паузы, статусная строка не обновляются; пользователь не получает ни
сообщения об ошибке, ни объяснения. Плюс непрерывный поток traceback в stderr
(5/с) — в запущенном из ярлыка приложении это мусор в журнале сессии.

Данные не теряются, приложение не падает, управление (кнопки, громкость,
переключение треков) продолжает работать: команды уходят в плеер, не отображается
только результат.

### 3.4 Рекомендация по исправлению

1. **Нормализовать длительность в слое снимка**, а не в вёрстке:
   `PlayerViewModel.snapshot()` не должен отдавать `None` в поле, объявленное
   как `int` (контракт `UiState` нарушается уже сейчас).
2. **Сделать `_mmss()` терпимым к `None`/`0`** — вернуть осмысленный маркер
   («—:--» или «0:00») вместо арифметики над `None`.
3. **Показать пользователю неизвестную длительность** явно: сейчас ползунок
   молча стоит на нуле, и перемотка невозможна без пояснения.
4. **Обернуть тело `refresh()` в защиту**: одно неверное поле не должно
   отменять обновление всего окна (кнопки, громкость, статус) — как уже сделано
   для кнопок через `guarded()`.
5. Не чинить это в одном PR с D-05: задачи независимы (D-06 — вычисление и
   отображение длительности, D-05 — маршрутизация ошибок команд).

### 3.5 Возможные регрессии после исправления

* Если неизвестную длительность показывать как «0:00 / 0:00», ползунок останется
  на нуле (сейчас это поведение `duration_ms=0`) — перемотка при неизвестной
  длительности останется недоступной; это ожидаемо, но нужно закрепить тестом.
* Изменение формата подписи времени может задеть существующие тесты и
  скриншоты; формат «—:--» стоит согласовать с дизайном, а не вводить
  молча.
* Если начать оборачивать `refresh()` в общий `try/except`, есть риск скрыть
  настоящие ошибки отрисовки — исключение стоит логировать, а не глотать.

### 3.6 Предлагаемые автоматические тесты приёмки

1. Юнит-тест `_mmss(None)` → без исключения, ожидаемая строка (и `_mmss(0)`,
   `_mmss(61_000)`).
2. Тест снимка: `PlayerViewModel.snapshot()` при треке с `duration_ms=None`
   возвращает `duration_ms` типа `int` (0) — контракт `UiState` соблюдён.
3. GUI-тест (offscreen допустим): трек с `duration_ms=None` → за 1 с в окне нет
   ни одного исключения, подпись времени обновляется, значок паузы меняется при
   паузе.
4. Тест на отсутствие «заморозки»: после исключения в одном поле остальные
   элементы окна (громкость, статус) продолжают обновляться.
5. Тест частоты: 5 с с треком без длительности → ни одного traceback в stderr.

## 4. D-05 — наблюдение: теряются ли ошибки асинхронных команд

**Это только наблюдение. Исправление не предлагается и в задачу к D-06 не
объединяется.**

### 4.1 Фактический путь исключения

```text
app.py: combo.currentIndexChanged → guarded("Выход", …)
      → vm.set_output(id)                     (viewmodel.py:249)
      → vm._cmd("output", action)             (viewmodel.py:196)
      → dispatcher.submit(...)                (dispatcher.py:94)
      → [отдельный поток] CommandDispatcher._execute  (dispatcher.py:186)
            command.result = command.action()   ← здесь бросается PlayerError
            except BaseException → command.error = exc
                                   stats["failed"] += 1
                                   if self._on_error is not None: …   ← on_error == None
      ← возврат в GUI-поток; command.error никто не читает
```

* `PlayerViewModel.__init__` создаёт `CommandDispatcher()` **без** `on_error`
  (`viewmodel.py:100-104`) → колбэка ошибки нет.
* `guarded()` в `app.py:135-139` ловит только исключения, возникшие
  **синхронно** в момент нажатия (например, «диспетчер закрыт»). Ошибка самой
  команды выполняется позже, в другом потоке, и в `guarded()` не попадает.
* `vm.last_error` (`viewmodel.py:103`) объявлен, но **нигде не заполняется** —
  остаётся `None`.
* Ошибка не превращается и в событие: очередь событий пуста, статусная строка
  не меняется.

### 4.2 Воспроизведение

Пользователь выбирает аудиовыход, которого уже нет (устройство отключили):

```bash

neurowave --provider local output --set выход-которого-нет-qa
# → «Нет такого аудиовыхода: выход-которого-нет-qa» + список доступных, код выхода 2
```

В окне приложения — тот же самый отказ через комбобокс «Выход»:

| Наблюдение | Значение |
|---|---|
| Счётчик `dispatcher.stats["failed"]` | 0 → **1** (команда действительно упала) |
| Статусная строка окна | **не изменилась** («NeuroWave QA — WO-03 test library» до и после) |
| `vm.last_error` | `None` |
| Очередь событий | пуста |
| `dispatcher._on_error` | `None` |
| Исключение в stderr | **нет** — ошибка не печатается нигде |
| Скриншот | `docs/qa/screenshots/triage02_d05_status_line.png` — в статусной строке только последнее событие, ошибки нет |

Вывод: в CLI тот же отказ показывается понятно (код 2, текст ошибки), в GUI —
исчезает бесследно. Разница в том, что CLI обращается к плееру напрямую, а GUI
проходит через `CommandDispatcher`, у которого в этой сборке нет получателя
ошибок.
